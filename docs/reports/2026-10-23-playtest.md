## Gameplay observations that remain

These are inherited rule/balance findings, not browser regressions. Changing
win conditions, reward rules or resolver thresholds would alter deterministic
save replay and the requested original mechanics; this playtest preserves them.
They should be resolved deliberately before calling the experience ready for
public release.

- **P1 progression:** five Reframes followed by repeated Validate can remain in
  crisis beyond turn 100. The observational core run stayed nonterminal through
  500 turns; BrowserSession remained actionable at 110 turns with progress 100,
  trust 100 and agitation 80. New game provides an explicit escape, but does not
  repair this balance trap.
- **P2 pacing/fairness:** repeated Validate succeeds at exactly 100 turns. With
  objective delivery the audit reached success with trust 0/agitation 45 and
  received 100 XP, 3 study and 50 cash. Completing 100 choices may feel repetitive
  even with varied prose; rewards do not necessarily reflect a satisfying arc.
- **P2 loadout choices:** four available cards fit into five slots. Removing
  cards only removes options in this case. The guide now explains keeping all
  four; deeper loadout tradeoffs are not implemented.
- **Replay motivation hypothesis:** one active case and fixed progression offer
  limited variety. The visuals and dialogue improve readability and atmosphere,
  but agent playtesting does not establish enjoyment. A short human playtest
  should assess when repetition begins, whether meter changes feel fair, and
  whether players want another session.

## Live AI result and release boundary

The in-app production browser used the supplied key only in memory. Explicit
model selections included Google Gemma 4 31B (free), Free Models Router and
NVIDIA Nemotron 3.5 Lightning (free). Requests were not silently retried or
substituted. None yielded a committed patient response; build
`73146661ca4f7dc629d8e658` (the same transport code before the final copy/tooltip
polish) reported **HTTP 404**, kept turn 0 and displayed an explicit retry alongside
the failure explanation ([screenshot](playtest-2026-10-23/live-provider-404.png)).
A separate bounded direct API diagnostic with the same privacy/zero-price
routing returned 404 and classified the error as **no endpoints matching the
data policy**, with an account-settings reference. Only those boolean
classifications and status were exposed; the response body and credential were
not written to files. This establishes an availability/account-policy blocker,
not successful live conversation quality.

The temporary key was explicitly forgotten through the UI after testing;
reload also demonstrated that it is absent while pending game state survives.
The final preview is left in local practice at turn 2 for review
([screenshot](playtest-2026-10-23/local-review-preview.png)). Credentials never enter
the generated static inventory or exported save schema.

**Hold deployment** until an approved account/provider setup can complete live
responses under the required privacy policy, and the inherited progression
trap/pacing findings above have been resolved or explicitly accepted. Review
OpenRouter account data-policy/model-access settings against the [official
routing documentation](https://github.com/OpenRouterTeam/docs/blob/main/guides/routing/provider-selection.mdx);
do not disable privacy restrictions merely to obtain a green test. Re-run live
conversation/coherence/cancellation acceptance after availability is restored.

GitHub Pages/DNS/HTTPS setup remains the documented separate administrator
step in [STATIC_HOSTING](../guides/STATIC_HOSTING.md). No external account,
DNS or publication setting was changed. No code was committed or pushed.
